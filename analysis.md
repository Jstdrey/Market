## 1) Резюме состояния системы
Приложение `Market` — локальный исследовательский стек для бэктестов криптовалютных стратегий в Streamlit с динамической загрузкой исторических свечей, ручным запуском бэктеста и перебором параметров. Архитектурно это трехуровневая связка:
- UI-оркестратор (`app.py`)
- вычислительный слой (`backtest/engine.py`)
- стратегический слой (`strategies/*`) + загрузчик (`utils/strategy_loader.py`)

Базовый поток “загрузка данных → backtest/optimization → визуализация + экспорт” реализован и рабочий. Есть важный прогресс: `app.py` уже хранит контекст прогона (`run_context`) и связывает его с отображением результатов, а `strategies/*` имеют `PARAMETER_SPECS`, на которых строится валидация параметров UI.

Сильная сторона системы — простая воспроизводимая последовательность действий для пользователя и достаточная модульность в плане добавления новых стратегий. Главный упор по рискам сейчас смещен в сторону качества эксплуатационной устойчивости: масштабируемость оптимизаций, качество валидаторов для сложных стратегий, безопасность динамического импорта и контроль целостности данных.

Критические улучшения уже начаты, но до “готового к регулярному production-like использованию” ещё есть шаги: детерминизм эксперимента, лимитирование ресурсоемкости и нормализация профилей/метаданных запуска.

## 2) Карта архитектуры (UI → orchestrator → движок → стратегии → данные)

```mermaid
flowchart LR
    U["Streamlit UI (app.py)"] -->|user inputs, запускает действия| O["Оrchestrator layer в app.py"]
    O -->|run_downloader| D["data/downloader.py + data/cache/*"]
    O -->|run_backtest / run_optimization| E["backtest/engine.py"]
    E -->|cerebro.addstrategy, run| S["strategies/*.py"]
    S -->|trades_log/equity| E -->|results dict| U
    O -->|strategy discovery| L["utils/strategy_loader.py"]
    O -->|profiles API (не в UI)| P["utils/profile_manager.py"]
```

Кратко по слоям:
- `app.py`: выбор символа/таймфрейма/даты, запуск данных, рендер графиков, табличек и экспортов.
- `backtest/engine.py`: загрузка/подготовка данных и запуск Backtrader (бэктест и оптимизация).
- `strategies/base_strategy.py`, `ma_cross_strategy.py`, `liq2_vwma_strategy.py`: поведенческий слой торговли и запись журналов.
- `data/downloader.py`: кэширование OHLCV и дозагрузка пробелов.
- `utils/strategy_loader.py`: динамический импорт классов стратегий.
- `utils/profile_manager.py`: хранение профилей параметров в JSON (фактически не подключено в UI).

## 3) Аудит вкладок UI

### 3.1. Вкладка **Data** (`show_market_data_tab`)
**Текущее состояние**
- Есть выбор `symbol`, `timeframe`, диапазона дат в боковой панели.
- Кнопка “Загрузить данные с Binance” запускает `run_downloader` в `data/downloader.py`.
- После загрузки выводится сводка (`Количество строк`, даты), таблица свечей и свечной график.

- Нет предпросмотра полноты/дефектов кэша в UI (нет индикаторов “дыры”, “версия формата”, “последняя нормализация”).

**Рекомендации**

## 4) Логика исполнения торговли, ордеров и позиций

### 4.1 Базовый слой логирования (`BaseLoggingStrategy`)
- `record_equity()` пишет `datetime + equity` на каждый бар и на `prenext`.
- `notify_order`: на `order.Completed` сохраняет `open_date/open_price/size` для buy и `exit_price/exit_date` для sell.
- `notify_trade`: при закрытии сделки пишет запись с `open_date/open_price/close_date/close_price/size/pnl/commission/pnl_after_commission`.

### 4.2 MA Cross (`MovingAverageCrossStrategy`)
- Индикаторы: SMA fast/slow + CrossOver.
- Сигнал входа: `crossover > 0`.
- Сигнал выхода: `crossover < 0`.
- Размер позиции рассчитывается как `available_cash / (price * (1+commission))`.

### 4.3 LIQ2 VWMA (`LIQ2VWMACompatibleStrategy`)
- Сложный входной стек: VWMA, RSI, SMI, EMA.
- Поддерживает entry_profile (official/hidden), DCA триггеры по просадкам, TP по профилю тренда, max_bars_in_trade, cooldown по losing streak.
- Есть внутреннее состояние по DCA и порядку входов/выходов.

### 4.4 Эквити и сделки
- Лог сделок строится по закрытым сделкам; это корректно для отчета, но не гарантирует покрытие незакрытых позиций.
- Эквити строится по всем барам через `broker.getvalue()`, что дает плавный капиталовый ряд и полезен для сравнения параметров.
- Экспорт CSV доступен для `trades_log.csv` и `equity_curve.csv`.

## 5) Качество кода и устойчивость

### 5.1 Валидация параметров
- Есть общий контракт для параметров через `PARAMETER_SPECS` в стратегиях и валидацию в UI (тип, min/max, lt/gt, choices).
- Для стратегий без `PARAMETER_SPECS` валидация деградирует до базового поведения.
- В `app.py` отсутствует строгая схема для бизнес-параметров (например единые типы обязательности/дефолтов/описаний).

### 5.2 Обработка исключений
- В бэктесте/оптимизации есть `try/except` с выводом пользователю.
- В цепочке загрузки данных `run_downloader` делает `sys.exit(1`; это плохо сочетается с долгоживущим Streamlit-сессией.
- Нет строгой матрицы ошибок по типу исключения и retry-политики для Binance API.

### 5.3 Кэширование данных
- Есть файловый cache per symbol/timeframe в `data/cache`.
- Появился `data_context` с `checksum`, `rows`, `size_bytes`, `context_version` (в `run_context` и валидации).
- Но нет централизованной политики инвалидации кэша по версиям стратегии/формата/источника.

### 5.4 Детерминизм и повторяемость
- `run_context` сейчас хранит run_id/run timestamp + data context checksum, что улучшает трассировку.
- Нет версии зависимостей/версии кода/seed для полной воспроизводимости.
- В `run_optimization` отсутствует фиксация состояния среды и результатов не гарантирует точную реставрацию без внешних файлов.

## 6) Безопасность и эксплуатационные риски

### 6.1 Динамический импорт стратегий
- `utils/strategy_loader.py` грузит все `.py` в `strategies`, выполняя код модуля на импорте.
- В локальном доверенном окружении это допустимо, но при совместном доступе папки к каталогу стратегии риск высокий.

### 6.2 Работа с локальными файлами
- Все важные артефакты (`data.csv`, кэш, `strategy_profiles.json`, `trades_log.csv`) локальные, в одной папке проекта.
- Нет политики ротации и целостности артефактов (кроме базового checksum для данных).

### 6.3 Логи и артефакты
- Есть runtime-логи Streamlit, но не структурированы и не содержат бизнес-контекста прогона.
- Содержимое `app_utf8_repair_tmp.py` и временных файлов может быть источником путаницы в деплойном/поддерживаемом состоянии.

## 7) Производительность и масштабируемость

- **Пузырек**: `run_optimization` растет комбинаторно с количеством параметров и размеров диапазонов (классический риск).
- **I/O**: чтение/сортировка больших `data.csv` (`SOL_USDT_5m.csv` около 15 МБ) может быть заметно тяжелым.
- **UI**: перерисовка графиков и табличек работает стабильно для средних объемов, но может тормозить при очень большом числовом числе строк.
- **Data cache**: наращивание количества пар/таймфреймов может привести к множеству файлов без TTL/политики очистки.

### Рекомендуемые ограничения на первую итерацию
- `max_combinations` для оптимизации (например 10k–100k).
- Предварительная оценка объема комбо: `len(range1)*len(range2)*...` + предупреждение перед стартом.
- Таймаут и “cancel” для длинных прогонов (хотя бы ручной stop via warning + reset state).

## 8) Риски (приоритеты P0–P3)

- **P0 — Детальная воспроизводимость недостаточна**
  - Не фиксируются версии кода/зависимостей и состояние окружения; есть только частичный data checksum.
- **P1 — Риск неконтролируемой оптимизации**
  - Отсутствуют ограничения на число комбинаций и время выполнения.
- **P1 — Безопасность динамического импорта**
  - Загрузка всех файлов из `strategies` без sandbox/подписи/allowlist.
- **P2 — Неполное разделение профилей и UI**
  - Есть инфраструктура профилей, но нет интерфейса их управления.
- **P2 — Ошибки API без soft-fail**
  - `sys.exit` в downloader и сырой UX при сетевых сбоях.
- **P3 — Разнородность кодировки и технических артефактов**
  - Присутствуют временные/восстановительные файлы (`app_utf8_repair_tmp.py`, .tmp_streamlit_*); это больше технический долг, чем production-critical.
