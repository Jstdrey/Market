# Аудит блока оптимизации (2026-04-08)

## Что проверено
- Весь UI-блок оптимизации в `app.py` (валидация диапазонов, подсчет комбинаций, callback прогресса, запуск движка, вывод результатов).
- Реальный прогон через приложение (Streamlit), а не через прямой вызов функции.
- Сценарий из запроса: `VWMA length` в диапазоне `50..90` (41 комбинация), остальные параметры фиксированы.

## Результаты прогонов через UI

### Сценарий A (полностью завершен)
- Пара: `BTC/USDT`
- Таймфрейм: `1m`
- Период: `2026-03-01 .. 2026-03-03` (4320 свечей)
- Комбинаций: `41`
- Время завершения: ~`110-113` секунд
- Наблюдение по процентам: шаг неравномерный на глаз (`2%, 5%, 7%...`), потому что это округление `completed/total`.

### Сценарий B (тяжелый, через UI не дождался финала в одном проходе)
- Пара: `SOL/USDT`
- Таймфрейм: `5m`
- Период в интерфейсе: `2024-01-01 .. 2026-01-01`
- Объем данных файла: `210 816` свечей (в ~48.8 раза больше сценария A)
- При попытке длительного UI-прогона сессия браузерной автоматизации обрывалась до завершения (на ~7-8 минуте), что подтверждает значительно большую длительность.

## Оценка времени ожидания для `VWMA 50..90`
- На легком наборе данных (BTC 1m, 4320 свечей): ~`1 мин 50 сек`.
- На крупном наборе данных (SOL 5m, 210816 свечей): ориентировочно `~1.5 часа` (линейная оценка по объему данных и числу комбинаций).
- На очень крупном наборе (`SOL 1m`, 1 054 080 свечей): оценка может уходить в `несколько часов`.

## Достоверность результатов оптимизации
- **Вычислительная достоверность**: высокая (расчеты детерминированы, `maxcpus=1`, прогон повторяемый на том же наборе данных).
- **Практическая полезность/устойчивость**: зависит от данных.
  - В прогоне BTC 1m (3 дня) все 41 комбинация дали одинаковый `PnL=0`, то есть оптимизация в этом окне фактически неинформативна.
  - Для реальной оценки нужны периоды с достаточным числом сделок и раздельная проверка in-sample/out-of-sample.
